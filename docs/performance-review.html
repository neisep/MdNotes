MdNotes Performance Review

Read-only review of the MdNotes .NET 10 / Avalonia 12 desktop app. Scope: allocations, hot-path LINQ, repeated I/O, UI-thread blocking, caching and object lifetime. Architecture was not reviewed and no source was changed.

Summary

The codebase is already deliberate about performance: one cached vault walk feeds the tree, the switcher and the search; note text is cached by write stamp; every keystroke-driven path is debounced; the preview's image and diagram caches are bounded and disposed. No blocking .Result or .Wait() calls exist and there is no logging in hot paths.

The remaining cost centres are concentrated in three places: the vault-wide search and replace scan (synchronous disk I/O on the UI thread, a folded copy of every note per scan, and extra file stats hidden behind a lookup), the preview rebuild (rebuilt even while hidden, per-run dynamic resource bindings, full-resolution image decode), and a few per-pointer-move tree walks in the sidebar drag path.

Findings

1. Vault-wide scans run synchronously on the UI thread

Severity
High
File
MdNotes/ViewModels/VaultWorkspaceViewModel.cs, MdNotes/ViewModels/SearchReplaceViewModel.cs, MdNotes/Services/VaultService.cs
Location
VaultWorkspaceViewModel.RunSearch (431-441), SearchReplaceViewModel.Rescan (98-132), VaultService.CurrentSnapshot (375-410) via RefreshTree
Status
Done · commit 89d3067
ProblemSidebar search, the replace rescan, and the tree walk (which reads the head of every note when UseNoteTitles is on) all execute on the UI thread from DispatcherTimer ticks. The first scan after opening a vault, or after an external tool touches many files, reads every note from disk on the UI thread.
ImpactThe window freezes for the duration of the scan. The debounce limits how often this happens, not how long each occurrence takes. It scales with vault size and disk latency (network drives, OneDrive placeholders).
RecommendationRun ISearchService.Search and ReplaceService.Find on the thread pool with a CancellationToken that the next keystroke cancels, and marshal results back. This needs a lock (or a per-scan copy) around NoteContentCache, which currently relies on being UI-thread-only. Verify the freeze length with a Stopwatch on a large vault first; for small local vaults the current design may be adequate.
Status · 2026-09-22

Done in 89d3067 (fix: review performance), on both halves. The unbounded walks — opening a vault and the watcher firing — go through RefreshTreeAsync → WalkAsync → Task.Run(_vault.GetTree), with a generation counter so a walk overtaken by a newer one drops its answer instead of writing it to the tree. ISearchService.Search and the replace rescan run under Task.Run with a CancellationTokenSource the next keystroke cancels, and NoteContentCache took the lock that made this safe.

Measured, and recorded in the source rather than here: the titled walk cost 244 ms over two thousand notes and 559 ms over five thousand, which is what settled the question this finding said to settle first. MdNotes.Tests/ScanBenchmark.cs is the harness, skipped unless MDNOTES_BENCH=1.

One path stayed synchronous on purpose. RefreshTree still runs on the UI thread at the call sites where the user just created, renamed, deleted or moved one entry, because the content cache holds every other note's head and the walk is therefore one disk read. That argument holds only while the cache is under budget — see finding 21.

Severity
High
File
MdNotes/Services/SearchService.cs, MdNotes/Services/VaultService.cs
Location
SearchService.Search line 20; VaultService.DisplayName (134-137) → CurrentSnapshot (375-410) → CurrentIgnore (344-359) → IgnoreFile.StampOf
Status
Done · todos.md task 53
ProblemDisplayName goes through CurrentSnapshot, which calls CurrentIgnore, which stats .mdnotesignore (and .gitignore when enabled) on every call. Search calls it once per note, so a scan performs one or two extra file stats per note on top of the content cache's own stat. The comment on CurrentIgnore says "one stat per enumeration", which holds for GetNotes but not for this per-note path.
ImpactTwo to three metadata syscalls per note per scan instead of one. On a few thousand notes this is tens of thousands of stats per debounce tick, in the same UI-thread window as finding 1.
RecommendationIn Search, take the snapshot once (e.g. expose IReadOnlyDictionary<string,string> Displays or a DisplayNames() accessor on VaultService) and look names up from it. Alternatively make DisplayName use the last published snapshot without re-checking the ignore stamp.

DisplayName and the new method share one lookup, so the title-or-file-name fallback is still defined once. Safe on the thread pool because a published snapshot is never written again.

Tested without a product seam: CurrentIgnore reads UseGitIgnore once per stat, so the settings fake counts the checks. One search now makes one check, where it made one plus one per note.

3. A folded copy of every note is allocated on every scan

Severity
High
File
MdNotes/Services/SearchService.cs, MdNotes/Services/MatchFinder.cs
Location
SearchService.Search line 24 (DiacriticFolder.Fold(content)) and 28-30; MatchFinder.FindLiteral line 71; MatchFinder.Find line 46 (new Lines(text)) and Lines.Build (132-138)
Status
Done · todos.md task 54 · measured: 29.2 MB allocated per keystroke on 5,000 notes, now 2.0 MB
ProblemFor every note whose text contains any foldable character (which is nearly every Swedish note), Fold allocates a full-length copy of the note. MatchFinder.Find also builds a line-start index over the full text for every note, including notes with zero matches. The content cache saves the disk read but the folded copy and the line index are recreated on every debounce tick.
ImpactAllocation traffic equal to the whole vault's text per scan (UTF-16, so twice the byte size), with notes over ~42K characters landing in the Large Object Heap and forcing gen2 collections. GC pauses add to the UI-thread time from finding 1.
RecommendationStore the folded text lazily alongside the raw text in NoteContentCache (fold once per read, not per scan), and build Lines lazily on the first match. A cheaper variant for Search: fold only the query and compare with a span-based loop that folds characters on the fly through the existing lookup table.
Status · 2026-10-03

Done, with the cached-fold option. NoteContentCache.ReadFolded folds a note on the first request after it is read and keeps the fold on the entry, so a save or an outside edit drops it with the text. Search and replace both use it, and MatchFinder builds Lines on the first match, for literal and regex alike.

The fold counts against the 32M-character budget when it is a copy (an all-ASCII note folds to itself and costs nothing). So a vault where every note has an accent fits about half as many notes, roughly 6,000 instead of 12,000, before scans fall back to re-reading. Not counting it would have broken the budget's one job.

Follow-up, 2026-10-03: the default budget went from 32M to 48M characters (96 MB of UTF-16) so the fold does not halve the vault the cache covers: roughly 18,000 plain notes, or 9,000 where every note has an accent. Pinned by The_default_budget_holds_eight_thousand_accented_notes.

Measured with ScanBenchmark, 5,000 generated notes, on Linux with old and new code on the same machine (medians): warm search 79.4 → 14.4 ms, replace find 33.8 → 14.9 ms, allocation while typing 29.9 → 2.0 MB per keystroke, Gen0/1/2 over nine keystrokes 29/29/2 → 3/2/2.

4. Content cache eviction is O(n) per evicted entry and thrashes on large vaults

Severity
Medium
File
MdNotes/Services/NoteContentCache.cs; same pattern in MdNotes/Views/Markdown/Lru.cs (25) and MdNotes/Models/NotePositions.cs (42)
Location
NoteContentCache.Put lines 81-86 (_entries.MinBy in a while)
Status
Done · commit 89d3067
ProblemEach eviction scans the whole dictionary with MinBy. When the budget (8M characters by default) is smaller than the vault, a sequential scan evicts on every read, so every note read costs O(entries), and because the scan is strictly sequential the LRU hit rate drops to zero: each note is evicted before it is asked for again.
ImpactVaults over ~8M characters (roughly 16 MB of Markdown) get no benefit from the cache and pay quadratic eviction overhead on every search. Smaller vaults are unaffected. The Lru and NotePositions copies of the pattern have capacities of 64 and 200 and do not matter.
RecommendationTrack recency with a linked list or an ordered structure so eviction is O(1), and either raise the budget in proportion to the vault or make it clear in settings that a vault larger than the budget is scanned from disk. Verify with a synthetic vault above the budget.
Status · 2026-09-22

Done in 89d3067 (fix: review performance), after 6c418c5. Recency is now a LinkedList<string> with the node stored on the entry, so eviction is O(1) and the victim is always the front of the list. The budget moved from 8M to 32M characters — 64 MB of UTF-16, about twelve thousand notes at the ~2.7 KB average it was measured against.

The numbers this finding asked for, quoted from the source comment: a warm search over a 5,000-note vault cost 1,196 ms against 154 ms for a 2,000-note one — eight times the work for two and a half times the notes, which is the quadratic this describes. HeldChars and BudgetChars are exposed so a benchmark can see the cache overrun rather than infer it.

Past the budget the cache degrades to re-reading rather than failing. The MinBy pattern in Lru.cs and NotePositions.cs was left alone as the finding advised.

5. Quick switcher re-flattens and re-ranks the whole vault per keystroke

Severity
Medium
File
MdNotes/ViewModels/QuickSwitcherViewModel.cs, MdNotes/Services/NameMatch.cs
Location
QuickSwitcherViewModel.RefreshResults (83-124), FlattenNotes (129-143), NameMatch.Rank (28-43)
Status
Done · todos.md task 61 · measured: 428 µs per keystroke on 5,000 notes — no felt lag
ProblemOnQueryChanged is not debounced (fine, it is in-memory), but each call allocates a new SwitcherItem per note plus folder-path strings, then ranks with a LINQ chain that sorts every candidate to take 50. Rank is called twice per note and each call folds both the candidate and the query, so the query is folded 2N times and each name is folded on every keystroke.
ImpactPer keystroke: N record allocations, up to 4N string allocations, and an O(N log N) sort. Noticeable typing lag in the switcher from a few thousand notes upward.
RecommendationCache the flattened list against the tree instance returned by GetTree() (it is the same reference until the vault changes), pre-fold names once when flattening, fold the query once per call, and replace the full OrderBy with a bounded top-50 selection or a bucket per NameRank.
Status · 2026-10-03

Done, although the baseline found no felt lag (428 µs): the allocation was the real cost, and the fix was contained. QuickSwitcherViewModel keeps its flattened rows, with both names pre-folded, against the tree instance GetTree() returned, and rebuilds only when it gets a different one. The query is folded once per keystroke through a new four-argument NameMatch.Rank overload; the two-argument one delegates to it, so there is still one rule. The full OrderBy became a heap bounded at 50, worst on top, ordered by rank, then name with the same culture-aware comparer the old ThenBy used, then tree order (what the stable sort gave). The empty-query list is computed once per tree.

One trap found while measuring: Enum.CompareTo takes object, and boxing the rank on every heap comparison was 350 KB per keystroke on its own; ranks are compared as ints now.

SwitcherBenchmarks, 5,000 notes (BenchmarkDotNet short job, Linux), against the baseline: broad query 394 µs / 8.8 KB (was 428 µs / 664 KB), narrow 34 µs / 560 B (was 251 µs / 536 KB), empty 1.3 µs / 3.9 KB (was 308 µs / 522 KB). The broad case's remaining time is culture-aware name comparison, kept for identical ordering. Tests: rows are reused until the vault changes, and the top 50 equal a full sort's over 280 notes spanning every rank tier, duplicate names included. The task 44 and task 50 tests pass unchanged.

6. Drag-over walks the whole tree twice per pointer move

Severity
Medium
File
MdNotes/Views/Shell/Sidebar.axaml.cs, MdNotes/ViewModels/VaultWorkspaceViewModel.cs, MdNotes/ViewModels/TreeNodeViewModel.cs
Location
Sidebar.OnDragOver (88-100) → Dragged (116-117) → VaultWorkspaceViewModel.FindNode (537-538); ResolveDrop → SiblingsOf (543-544) → FindNode; Sidebar.RowUnder (140-144); TreeNodeViewModel.SelfAndDescendants (66-72)
Status
Done · todos.md task 62 · measured: 129 µs and 304 KB per tree walk on 5,000 notes, twice per pointer move
ProblemEvery DragOver event (fired continuously while dragging) resolves the dragged path with FindNode, then ResolveDrop finds the parent with a second FindNode. FindNode is SelectMany over a recursive iterator, which costs O(depth) per yielded node. RowUnder adds a LINQ pass over visual ancestors of every hit visual. SelectPath (512-519) also walks all nodes and allocates a string per folder via IsSameOrUnder.
ImpactTwo full tree walks plus LINQ allocations per pointer move during a drag. Smooth on a few hundred rows; stutters on several thousand.
RecommendationResolve the dragged node once on drag start and keep it in a field; give TreeNodeViewModel a Parent reference so siblings need no lookup; and keep a path→node dictionary refreshed in Reconcile for FindNode (the comparer must stay OrdinalIgnoreCase as the current lookup is). Replace the recursive iterator with an explicit stack.
Status · 2026-10-03

Done. TreeNodeViewModel.Parent is set when a row is created and never changes, because a row that moves is a new row by path. SiblingsOf, ParentFolder and SelectPath's ancestor expansion all follow it now: SelectPath walks up from the node instead of testing every folder in the vault against the path. FindNode is a lookup in a path index (OrdinalIgnoreCase, first row in drawing order wins, as the old FirstOrDefault did) rebuilt after every reconcile and cleared on a vault switch. The recursive SelfAndDescendants became an explicit-stack TreeNodeViewModel.Walk with the same order.

DragBenchmarks, 5,000 notes (short job, Linux): the lookup is 38 ns, nothing allocated, where the walk is 88 µs / 107 KB (122 µs / 304 KB in the baseline, before the iterator change), twice per pointer move. The index costs 0.27 ms to rebuild once per reconcile, against a reconcile that already walks the vault.

Two parts of the recommendation were deliberately not done. Caching the dragged node at drag start: with an O(1) lookup it saves nothing, and a cached row could outlive a refresh that removed it. Sidebar.RowUnder's LINQ over visual ancestors: it stops at the first row border under the pointer, a handful of visuals, so it is not where the cost was. Drop policy and Alt+↑/↓ are unchanged; their tests (TreeOrderTests, SidebarDragTests) pass as they were.

12. Mermaid renders synchronously per keystroke inside a fence

Severity
Medium
File
MdNotes/Views/Markdown/DiagramView.cs, MdNotes/Views/Markdown/DiagramCache.cs
Location
DiagramView constructor line 38 (cache.NaturalSize); DiagramCache.GetPicture (28-29), capacities on line 17
Status
Done · todos.md task 59 · measured: 4.4 ms per changed diagram, 81% of it in SvgSource.LoadFromSvg
ProblemEvery edit inside a ```mermaid fence produces a new source string, so each 250 ms tick renders Mermaid → SVG → SvgSource synchronously in the DiagramView constructor, then rasterizes a bitmap on first layout. Each intermediate typing state is cached as an unmanaged SvgSource picture (up to 64) and bitmap (up to 32) until evicted.
ImpactUI stalls while typing in a diagram, and up to 64 stale vector pictures plus 32 stale bitmaps of half-typed diagrams held in unmanaged memory. Bounded, so not a leak, but the bound is generous for transient states.
RecommendationMeasure first: time MermaidRenderer.RenderSvg + SvgSource.LoadFromSvg for typical diagrams. If it is more than a few milliseconds, render the SVG on the thread pool and show the previous bitmap until it arrives. Consider a smaller picture capacity, since only the diagrams in the current note need to be hot.
Status · 2026-10-03

Done. Measured first, as asked: the whole DiagramView constructor path for the 13-node flowchart was 8.7 ms on this Linux machine (short job, wide error bars), 4.4 ms in the Windows baseline, and SvgSource.LoadFromSvg was most of it both times, past the “more than a few milliseconds” bar. So an edited diagram now renders on the thread pool. DiagramSlots remembers what each Mermaid block showed in the last build, by position; when a block's source changes and its previous picture is cached, the build shows that previous picture and calls DiagramCache.LoadInBackground. When the render lands back on the UI thread, the view rebuilds only if the latest build is still waiting for that exact source, and the rebuild then finds it in the cache. A render the user has typed past is disposed rather than cached, which answers the retention half of the finding without shrinking the capacities (a note with many diagrams would otherwise thrash). A note's first showing stays synchronous: there is nothing to show meanwhile, and a blank box that fills in is worse than 5 ms.

Background failures are remembered (bounded at 64), because the landing triggers a rebuild, and a forgotten failure would be retried by that rebuild forever. Good practices

  • One walk, one snapshot. VaultService.CurrentSnapshot answers the tree, the note list, folders and display names from one cached walk, invalidated by revision. The walk runs outside the lock so the watcher thread never stalls.
  • Content cache keyed by write stamp (NoteContentCache) with explicit Store after the app's own writes, bounded by characters rather than count. The stamp check is exactly one FileInfo per read.
  • Debouncing everywhere it matters: preview 250 ms, search 250 ms, replace rescan 250 ms, watcher refresh 300 ms, diagram re-rasterize 150 ms after resize. MarkdownView.QueueRebuild coalesces several property changes into one rebuild per dispatcher pass.
  • Tree reconciliation (TreeNodeViewModel.Reconcile) keeps existing rows and uses Move instead of remove-and-insert, so a refresh does not regenerate containers or lose expansion state.
  • Watcher filters exclude LastWrite so autosaves do not rebuild the tree, and IsQuiet drops events under excluded folders without touching the disk.
  • Unmanaged memory is owned: DiagramCache and ImageCache are bounded, dispose what they evict, and are disposed with the window. DiagramView borrows bitmaps by key rather than holding them. Leak tests exist for the replaced preview tree.
  • Regex hygiene: GeneratedRegex in SvgCssInliner and NoteTemplate, a compiled WordRegex, a 2-second match timeout on user patterns in MatchFinder, and a deliberate choice not to compile short-lived ignore patterns.
  • Length-preserving diacritic folding via a lookup table, with a fast path that returns the original string when nothing folds.
  • No blocking async (.Result, .Wait()) anywhere; async void is confined to UI event handlers. No logging in hot paths.
  • NoteTitle.From scans only the first 4096 characters; MatchFinder.Apply splices with a pre-sized StringBuilder; ReplaceService.StillMatches compares spans without allocating.

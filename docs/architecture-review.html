1Executive Summary

MdNotes is a coherent, deliberately-layered application. The dependency direction is strict and one-way, the domain and service layers contain no UI types at all, filesystem conventions are each owned by exactly one class, and the composition root is a single explicit file with no container. For a 5 000-line desktop app this is the right shape, and most of it should be left alone.

The strain is concentrated in three places, and they are related:

  • Vault identity is process-global mutable state, but every window keeps its own copy of it. One VaultService is shared across all windows; opening a different vault in one window mutates the root for all of them and tells none of them. This is the only finding in the report that can produce wrong behaviour rather than merely slow or awkward behaviour.
  • There is no index, and every read is synchronous on the UI thread. Four independent code paths each walk the vault and re-read files from disk — sidebar search does it per keystroke, undebounced. The app has no background I/O at all outside the single-instance pipe.
  • MainViewModel is a god object with nine constructor dependencies, four child view models and the app's only error funnel — and that constructor is written out verbatim at ten test call sites.

On complexity: the architecture is mostly right-sized, but there are four interfaces with a single implementation and no test double (IVaultService, ISearchService, IReplaceService, IMarkdownRenderer) that currently buy nothing — while six other interfaces in the same folder have real second implementations and clearly earn their place. The more expensive duplication is not in the abstractions but in the view layer, where the three modal overlays are copy-pasted chrome, three independent theming mechanisms coexist, and diagram colours are a second palette that does not follow the first.

The one-line verdict. This is a well-designed small application whose growth has outpaced two of its foundations: a shared-mutable vault handle that was never designed for multiple windows, and a read-everything-every-time data access pattern that was fine at one feature and is now behind four. Neither needs a rewrite; both need a decision about ownership.

2Current Architecture

Shape

A single-process Avalonia desktop app, MVVM via CommunityToolkit.Mvvm source generators, organised in four folders that map exactly onto four layers:

LayerContentsDepends onUI types?
Models/Pure data and pure text rules — VaultEntry, SearchOptions, TextMatch, VaultIgnore (the whole ignore-pattern language), NoteTemplate (placeholder substitution + path normalisation)nothingnone
Services/Filesystem and text: VaultService, SearchService, ReplaceService, MatchFinder, NoteTemplateService, VaultIgnoreService, JsonSettingsService, plus the format-owners IgnoreFile, FolderOrderFile, PathScope, DiacriticFolderModelsnone (grep-verified)
ViewModels/MainViewModel + four children: EditorViewModel, SettingsViewModel, QuickSwitcherViewModel, SearchReplaceViewModel; plus TreeNodeViewModelServices, ModelsAvalonia.Threading (timers), GridLength
Views/Shell (Ribbon, Sidebar, PaneHeader, StatusBar), three modal overlays, two dialogs, and a hand-written Markdown rendering engine under Views/Markdown/everythingyes

Composition and lifetime

Program.cs attempts a single-instance hand-off over a named pipe before any UI exists, then starts Avalonia. App.axaml.cs:30-51 builds a DialogService, installs a global UI-thread exception handler, plants the diagram renderer into a static on MarkdownView, and constructs AppSession.

AppSession.cs is the composition root and the only place services are instantiated. It holds one of each service for the process — including one VaultService, so one FileSystemWatcher pair and one settings file serve every window — and creates one MainViewModel + MainWindow per open subject (AppSession.cs:46-63). A second launch does not start a second process; its file arrives over the pipe and becomes another window (App.axaml.cs:45-48). Wiring is hand-written constructor injection; there is no DI container, and no view ever resolves a service.

Where state lives

The filesystem is the source of truth. There is no in-memory model of the vault that survives a refresh: MainViewModel.RefreshTree discards the whole Tree collection and rebuilds it from _vault.GetTree() on every change. Two sidecar conventions extend the filesystem rather than shadowing it — .order per folder for manual ordering, and .mdnotesignore at the root for exclusions. User preferences live in one JSON file under ApplicationData, written through on every property set.

Background and async work

There is effectively none. SingleInstance.Listen() is the only Task.Run in the application. Every vault read, walk, search and write happens synchronously on the UI thread. DispatcherTimer is used for debouncing in three places (preview 250 ms, autosave configurable, tree refresh 300 ms, rescan 250 ms) — these defer work but do not move it off the thread. The only genuinely asynchronous surface is IDialogService, which is async because modal dialogs are.

Search and indexing

There is no index. Every query walks the directory tree and reads matching files from disk at the moment it is asked. Four separate code paths do this, each with its own matching rules (see F7). The exclusion list is the only caching layer: a compiled VaultIgnore kept behind a stamp of the ignore files' size and mtime (VaultService.cs:225-239), which is checked once per enumeration rather than per entry.

Error propagation

Services throw; MainViewModel.Guard/GuardAsync (MainViewModel.cs:572-594) catch and show a dialog. Two subsystems deliberately never throw — IgnoreFile and NoteTemplateService resolve every failure to "nothing configured", on the reasoning that a broken template must not block note creation. A second, process-wide catch-all sits in App.axaml.cs:33-37 (see F12).

4Critical & High Findings

F1

One shared VaultService feeds N windows, and switching the vault invalidates none of them

CriticalConf: HighFixed

Finding. Vault identity is process-global mutable state on a single shared service, but each window's MainViewModel keeps its own derived copy of that identity. Changing the vault in one window mutates the root for every window and notifies no one.

Evidence
  • AppSession.cs:32 — one VaultService for the process; the class comment at :10-11 states the intent: "Windows share the vault, so the file watcher and the settings file are opened once however many windows are up."
  • AppSession.cs:46-63 — NewWindow creates a fresh MainViewModel per window, all handed the same _vault.
  • MainViewModel.cs:499-510 — OpenVaultAt calls _vault.Open(path), then sets its own VaultPath, VaultName, clears its own SearchQuery/SelectedNode and rebuilds its own Tree. Nothing is broadcast.
  • VaultService.cs:18-57 — Open disposes and recreates both watchers and reassigns RootPath, but never raises VaultChanged.
  • MainViewModel.cs:59 — HasVault => _vault.RootPath is not null reads the shared value, while VaultName (:56) is a per-window cached string.
Why it matters

After window A opens a different vault, window B is in a genuinely inconsistent state: its sidebar and title still name the old vault, but every operation it performs resolves against the new root. The next watcher event — a file created anywhere in the new vault — fires MainViewModel._vaultChanged in window B too (MainViewModel.cs:113-118), and its 300 ms timer calls RefreshTree, which repopulates B's tree from the new vault while B's header still reads the old name.

The knock-on is worse than cosmetic. EditorViewModel.IsLooseFile (EditorViewModel.cs:41-42) is computed as "is my path under _vault.RootPath", and SaveMode (:48) returns Manual for a loose file regardless of the user's setting. So switching vaults in window A can flip window B's open note from autosaved to manual-save, or the reverse, with no visible cause — the status bar text (SaveStatus, :51-58) will not even update, because nothing raises PropertyChanged for it.

This is the one finding in the report where the consequence is incorrect behaviour rather than cost.

Suggested direction

Decide whether the vault is a process-level singleton or a window-level subject, and make the code say so. If it stays shared, vault identity should be a single observable owned by the service — windows should read it rather than cache it, and Open should announce itself on the same channel VaultChanged already uses, so the existing per-window refresh path handles it for free. If instead each window may hold its own vault, the sharing in AppSession is the thing to unwind, and the cost is one watcher pair per window. The middle position — shared handle, cached copies, no notification — is the only one that cannot be made correct.

Status · 2026-09-21

Fixed in f455fa9 (review phase 1), by the first of the two options offered. VaultService raises VaultOpened after Open retargets the vault (VaultService.cs:29,82), and the per-window copies are gone: VaultPath, VaultName and HasVault now read _vault.RootPath (VaultWorkspaceViewModel.cs:63-70). OnVaultOpened (:458) resets the title, the tree, the search and the one-step undo, and calls _editor.NotifyVaultChanged() — which closes the IsLooseFile/SaveMode knock-on this finding described.

F2

No index, and every vault read is synchronous on the UI thread

HighConf: HighFixed

Finding. The application has no background I/O. Four independent code paths each walk the vault and re-read files from disk on demand, and the highest-frequency one is driven directly by keystrokes with no debounce.

Evidence
  • Grep across MdNotes/: the only Task.Run in the application is SingleInstance.cs:51. No async method exists anywhere in Services/.
  • MainViewModel.cs:475-483 — OnSearchQueryChanged calls _search.Search(value) directly on every keystroke. SearchService.Search (SearchService.cs:9-31) enumerates every note and calls vault.Read(path) on each, then folds diacritics over the whole content. No DispatcherTimer guards this path, though three other paths in the app have one.
  • QuickSwitcherViewModel.cs:73-84 — OnQueryChanged → RefreshResults → _vault.GetTree(), a full recursive directory walk, per keystroke.
  • VaultIgnoreService.cs:42-53 — Probe() ends in vault.EnumerateNotes().Count(), a whole-vault walk. It is called from SettingsViewModel.ExcludeStatus (SettingsViewModel.cs:90-105), which is re-read whenever the panel opens and on every edit to the pattern text.
  • SearchReplaceViewModel.Rescan (:98-132) is debounced 250 ms, but still runs _replace.Find — read-every-note — synchronously on the UI thread.
  • MainViewModel.RefreshTree (:512-527) discards and rebuilds the entire tree, triggered by a 300 ms timer on any watcher event.
Why it matters

Cost scales with vault size on a thread that must stay responsive. Typing five characters into the sidebar search box reads every note in the vault five times. The exclusion feature exists precisely because people point MdNotes at folders containing node_modules and code repositories — and it correctly prevents descending into them (VaultService.cs:272-289) — but for the notes that remain, the per-keystroke full read is unchanged.

Architecturally the more important consequence is that there is nowhere to put an index. Each of the four paths owns its own traversal and its own matching, so introducing caching means changing four things, and any future feature that needs to ask a question about the vault (backlinks, tags, a graph view, note counts) has no choice but to add a fifth walk.

Suggested direction

The smallest useful move is not an index — it is to give the vault a single place where "what is in this vault" is answered, so that the answer can later be cached, invalidated by the watcher that already exists, and computed off-thread without touching four call sites. The existing VaultIgnore stamp-and-cache mechanism (VaultService.cs:225-239) is a working precedent for exactly this pattern in this codebase. Debouncing sidebar search is a separate, much smaller fix, and it does not address the underlying structure.

Status · 2026-09-21

Partly fixed in 9bf07e5 (review phase 2). The structural half — the part this finding called the more important one — is done: GetTree, GetNotes and GetFolders all read one cached VaultSnapshot, invalidated by a revision counter and the watcher that already existed (VaultService.cs:323-349). That is the single place the report asked for, built on the stamp-and-cache precedent it pointed at. Sidebar search is debounced 250 ms (VaultWorkspaceViewModel.cs:414), the quick switcher and VaultIgnoreService.Probe read the snapshot instead of re-walking, and note images are cached across preview rebuilds.

The rest followed in todos.md task 47, as a content cache rather than as background I/O — the snapshot cached paths, this caches the text. Services/NoteContentCache.cs sits behind VaultService.Read, so all five readers benefit from one change; it is keyed by path plus write stamp, bounded by total characters, and the app's own writes are put in directly rather than left for a stamp to notice. Measured over 2000 notes: 267 ms per search to 91 ms.

What the measurement then showed: 61 of those 91 ms is the FileInfo stat — 2000 syscalls asking whether anything changed — and only ~30 ms is the fold and the match. The freshness check can be removed by carrying NotifyFilters.LastWrite into a handler that drops one content entry without rebuilding the tree, but that trades a syscall for trusting the watcher, so it is left as a decision rather than taken as a tuning. The application still has no background I/O, which remains true of every path here.

F3

MainViewModel has become the god object, and its constructor is the blast radius

HighConf: HighFixed

Finding. One class holds nine service dependencies, owns four child view models, and mediates every feature in the application. Because it is constructed by hand at every test site, each new dependency is a mechanical edit across the test suite.

Evidence
  • MainViewModel.cs is 595 lines — the largest file in the project, 12% of all source.
  • Constructor :66-75 takes nine parameters: IVaultService, ISearchService, IReplaceService, ISettingsService, IDialogService, IMarkdownRenderer, IFileAssociationService, INoteTemplateService, IVaultIgnoreService.
  • Responsibilities in one class: vault open/restore, note and folder CRUD, rename, delete, wikilink resolution, drag-and-drop resolution (ResolveDrop :414-435), manual reordering, tree rebuild and selection restoration, sidebar search, view mode, theme mode, loose-file handling, import, file-association registration, and the app's only error funnel (Guard/GuardAsync :572-594).
  • The nine-argument call is written out verbatim at ten sites: MainWindowTests.cs:30,73,143,185,231, NavigationLeakTests.cs:29, SidebarDragTests.cs:72, ExcludeTests.cs:23, LooseFileTests.cs:39, WikiLinkFolderTests.cs:108.
Why it matters

This is the concrete mechanism by which a small change reaches unrelated areas. The two most recent features each added one dependency, and each therefore touched every test that constructs a window — including tests about diagram caching and drag ordering, which have nothing to do with templates or exclusions. The class is still readable, and the Guard discipline is genuinely good, but the growth vector is clear and unbounded: nothing in the current structure suggests where feature number ten would go instead.

Suggested direction

Two things are being conflated: the window's shell state (view mode, theme, sidebar, title) and the vault workspace (tree, selection, CRUD, navigation, search). They have different lifetimes and different dependencies — the shell needs settings and dialogs; the workspace needs the vault, search, templates and exclusions. Splitting along that seam would let each half be constructed and tested on its own. The cheaper, non-architectural palliative is a single test helper that builds a default MainViewModel, which removes the blast radius without addressing the size.

Status · 2026-09-21

Fixed in 9bf07e5 (review phase 2), along exactly the seam this finding proposed. MainViewModel is 180 lines and holds the shell only; everything vault-shaped moved to VaultWorkspaceViewModel (544 lines) and the open note to EditorViewModel (227). The nine-parameter constructor is now MainViewModel(AppServices) — a record whose own doc comment records the fourteen-site edit that caused it. The tenth service, IDiagramRenderer, was one field.

F4

Image rendering reads arbitrary paths off the UI thread's critical path, with no vault containment

HighConf: HighFixed

Finding. The inline renderer resolves image URLs against the note's directory and opens them directly during layout construction. There is no containment check against the vault root, and the decoded bitmap is never disposed.

Evidence
  • InlineRenderer.cs:176-183 — ResolveImagePath combines ctx.BaseDirectory with the URL and calls Path.GetFullPath. It rejects non-file absolute URIs, but nothing rejects a relative path that climbs out of the vault: ../../../../etc/… normalises cleanly and passes the File.Exists test.
  • Services/PathScope.cs exists for exactly this check and is used by the vault, the editor and the tree — but is not used here.
  • InlineRenderer.cs:162 — Source = new Bitmap(path): a synchronous file open and image decode inside InlineUIContainer construction, i.e. during the UI-thread render pass. MaxWidth = 800 bounds the displayed size, not the decode.
  • The Bitmap has no owner and is never disposed; unlike diagram bitmaps, it is not held by DiagramCache.
  • Grep confirms this is the only filesystem access in the entire view layer, which is otherwise clean.
Why it matters

Two distinct consequences. Structurally, it is the single hole in an otherwise strictly-observed rule that views do not touch the disk — and being the only one, it is the one most likely to be overlooked when the rule is next reasoned about. Behaviourally, a note containing a large image blocks the render pass while it decodes, and a note containing many of them repeats that on every rebuild; since the preview rebuilds on a 250 ms timer while typing (EditorViewModel.cs:15), images are re-decoded repeatedly during editing.

The containment gap is worth stating plainly and without inflation: notes are local files the user already owns, so this is not a privilege boundary being crossed. It matters because a vault may be synced or shared, and because every other path-handling site in this codebase is careful about exactly this — NoteTemplateService.cs:39-46 normalises before comparing specifically to stop root/../../x passing a prefix test.

Suggested direction

Route image resolution through the same containment test the rest of the app uses, and give decoded images the same ownership story diagrams already have — a bounded cache that owns the lifetime — rather than an unowned object created during layout.

Status · 2026-09-21

Fixed in 9bf07e5 (review phase 2), on both counts. Containment: Services/NoteImagePath.cs normalises with GetFullPath before testing with PathScope.IsSameOrUnder — and defaults to the note's own folder when no root is given — with InlineRenderer.AddImage (:149) resolving through it. Ownership: Views/Markdown/ImageCache.cs is a bounded LRU that owns and disposes its bitmaps, keyed by path plus the file's write stamp, so a preview rebuild no longer re-decodes.

The ownership split this shared with F11 was closed separately in todos.md task 49. Borrow-per-draw was not available — an Image holds its Source for as long as it is on screen — so the bound changed in kind: ImageCache is bounded by build rather than by count, and disposes a bitmap only once two builds in a row have gone without it, by which time no tree that could hold it is on screen. Nothing the current build asked for is ever disposed, which is what a count bound could not promise: 30 images in one note used to throw ObjectDisposedException out of Image.MeasureOverride against the bound of 24.

Remaining: a cache miss still decodes on the render pass, which is the part of this finding that overlaps F2 and is not addressed.

5Medium & Low Findings

F5

Four interfaces have one implementation, no test double, and no substitution point

MediumConf: HighResolved

Finding. IVaultService, ISearchService, IReplaceService and IMarkdownRenderer each have exactly one implementation and are never substituted — not in production, not in tests.

Evidence
  • Implementation count by grep: IVaultService → VaultService only; ISearchService → SearchService only; IReplaceService → ReplaceService only; IMarkdownRenderer → MarkdownRenderer only.
  • Tests pass the concrete classes: MainWindowTests.cs:30 constructs new SearchService(vault.Service), new ReplaceService(vault.Service), new MarkdownRenderer(), and TempVault.cs:13 exposes a real VaultService over a temp directory.
  • Fakes.cs contains doubles for five interfaces — FakeSettings, FakeTemplates, FakeExclusions, FakeDialogs, FakeFileAssociation — and for none of these four.
  • IVaultService is a 56-line interface whose XML documentation carries the real design reasoning, duplicated in comments on the implementation.
Why it matters

Each is an extra file to keep in step and an extra indirection when reading a call chain, in exchange for a seam nothing uses. The contrast inside the same folder is the strongest argument: the six other service interfaces all have genuine second implementations — IFileAssociationService has a Windows and a non-Windows one, IDialogService has a real and a recording one, IDiagramRenderer has a counting test double, and ISettingsService, INoteTemplateService and IVaultIgnoreService all have fakes that let view-model tests run without a disk. Those earn their keep; these four currently do not.

One nuance worth recording rather than glossing: IVaultService is the dependency every other service takes, so it is the interface most likely to be wanted as a seam. That it has no fake despite 31 test files is evidence that the real one over a temp directory is genuinely good enough — which is a finding about the tests' quality, not a gap in them.

Suggested direction

These are candidates for removal in favour of the concrete class, not for adding implementations to justify. The decision is per-interface and depends on whether a second implementation is actually foreseen; on the evidence in this repository, none is. Removing them is a mechanical change with no behavioural risk, and it shortens every call chain the reader has to follow.

Status · 2026-09-21

Resolved in 0e253e3, by removal as suggested. IVaultService, IReplaceService and IMarkdownRenderer were deleted in favour of the concrete classes; AppServices names those three directly. ISearchService was kept deliberately, and now meets this finding's own criterion: CountingSearch (SidebarSearchTests.cs:180) is a genuine second implementation, used to assert that sidebar search is debounced.

F6

Tree selection and expansion exist in two places and are reconciled by hand on every refresh

MediumConf: HighFixed

Finding. Because the tree is discarded and rebuilt from disk on every change, all per-node UI state has to be captured before the rebuild and replayed after it — and selection is simultaneously held on the parent view model and on each node.

Evidence
  • MainViewModel.SelectedNode (:39) and TreeNodeViewModel.IsSelected (TreeNodeViewModel.cs:15) both exist; OnSelectedNodeChanged (MainViewModel.cs:457-468) clears the flag on the old node and sets it on the new one.
  • RefreshTree (:512-527) collects expanded paths into a HashSet<string>, clears Tree, rebuilds every TreeNodeViewModel from VaultEntry records, then replays expansion and re-resolves the selection by path — falling back to the open note when the selection has vanished.
  • TreeNodeViewModel.IsDropTarget (:16) is a third piece of view state on the node, set and cleared from the view (Sidebar.axaml.cs:144,161), with the sidebar keeping its own _highlighted back-pointer (:20) purely to undo the mutation it made.
Why it matters

Every piece of per-node state must be individually remembered across a rebuild or it is silently lost, and the rebuild happens on a 300 ms timer after any filesystem event. Expansion and selection are handled; scroll position and IsDropTarget are not. Adding a fourth piece of node state (a checkbox, a dirty marker, an inline rename box) means remembering to extend RefreshTree, and forgetting produces a bug that only appears when an unrelated file changes on disk.

The rebuild-everything approach is a defensible choice for a tree of this size and it makes external-change handling trivially correct — the cost is precisely this manual state preservation, which is the kind of thing that decays.

Suggested direction

Either reconcile the existing tree against the new one by path instead of replacing it, so node state survives by construction; or keep the rebuild and make the preserved state explicit and singular — one object describing "what the sidebar remembers", captured and restored in one place, rather than per-property code inside RefreshTree. Selection itself should have one owner: the node flag can be derived from the view model's SelectedNode rather than mirrored.

Status · 2026-09-21

Fixed in c970b91 (review phase 3), by the first of the two directions offered — reconcile rather than replace. TreeNodeViewModel.Reconcile (:28) matches the entries read off disk onto the rows already there by path, and moves rather than remove-and-inserts, so the TreeView keeps the container and every piece of node state survives by construction. Nothing is replayed. Selection now has one owner: IsSelected is gone from the node, and so is IsDropTarget — the drop highlight is view-local (Sidebar.axaml.cs:148), with no back-pointer on the view model.

F7

Four matching implementations, and the same name-resolution rule written three times

MediumConf: HighFixed

Finding. Four separate code paths answer "which notes match this text", each with its own traversal and its own rules. The specific rule "an exact match wins, an accent-folded match is the fallback" is implemented three times.

Evidence
  • SearchService.Search (SearchService.cs:9-31) — folded substring over content, first match only, plus a filename fallback; produces a snippet.
  • MatchFinder (MatchFinder.cs:43-96) — literal-folded or regex, whole-word, all matches with offsets and line context. Used by search-and-replace only.
  • QuickSwitcherViewModel.RefreshResults (:78-133) — its own folded ranking, exact → prefix → contains, capped at 50.
  • VaultService.FindNoteByName (:71-85) and FindFolderByName (:87-101) — exact-then-folded, for wikilink resolution. The two methods are near-identical in shape, and the comment "An exact name always wins … folding accents away is only a fallback" appears in both.
Why it matters

The four are not gratuitous — they genuinely produce different outputs, and PLAN.md records that MatchFinder was introduced deliberately because SearchService reported only the first match per note and was therefore unusable as the basis of a replace. But the consequence is that a user-visible rule now lives in three places: if accent-folding, case sensitivity or tie-breaking changes, it has to be changed in all three or sidebar search, the quick switcher and wikilinks will quietly disagree about which note a word names.

The strongest counter-evidence, and it should be respected: MatchFinder is explicitly designed as the single matcher behind both the replace preview and the write (MatchFinder.cs:7-10), which is a real correctness invariant. The problem is not that matchers exist; it is that name resolution was never extracted the way span finding was.

Suggested direction

Extract the name-matching rule — exact beats folded, case-insensitive — into one place the way DiacriticFolder and PathScope already are, and let the vault lookups and the quick switcher share it. The three content-matching paths are better left distinct until they share a traversal (see F2); collapsing them before that would couple them without removing the real cost.

Status · 2026-09-21

Fixed — todos.md task 44. Services/NameMatch.cs holds the rank ladder (Exact / ExactFolded / Prefix / PrefixFolded / Contains / ContainsFolded), next to PathScope and DiacriticFolder as this finding suggested. VaultService and QuickSwitcherViewModel both call it; the three restatements are gone.

F8

Process-global render state lives on a control, outside the composition root

MediumConf: HighFixed

Finding. The diagram renderer and its cache are static mutable members of the MarkdownView control, set from App rather than injected, and the cache is replaced without disposing what it held.

Evidence
  • MarkdownView.cs:31 — public static IDiagramRenderer? DiagramRenderer { get; set; }, written at App.axaml.cs:39 and re-written by tests (MainWindowTests.cs:31, MarkdownViewLeakTests.cs:22, NavigationLeakTests.cs:30).
  • MarkdownView.cs:27 — private static DiagramCache? _diagrams; the real picture and bitmap cache for the whole process.
  • MarkdownView.cs:84-90 — Diagrams() recreates the cache only when the renderer identity differs: if (_diagrams?.Renderer != renderer) _diagrams = new DiagramCache(renderer);. The previous cache — up to 64 SvgSources and 32 Bitmaps, all IDisposable — is dropped without disposal. It is also never cleared when a window or vault closes.
  • MarkdownView.cs:87 throws if the static was never set, so the control has a hidden initialisation order requirement on App.
Why it matters

This is the one place where the otherwise-exemplary composition root is bypassed: every other dependency in the app arrives through a constructor from AppSession. The practical costs are a test-ordering hazard (tests must set the static, and a test that swaps the renderer silently abandons the previous cache's unmanaged Skia memory), and a cache whose lifetime is the process rather than the session.

Context matters here: PLAN.md records that DiagramCache was introduced specifically to fix a measured unmanaged leak in Svg.Skia, with regression tests. The cache is well-built — bounded, keyed, disposing on eviction. The problem is only where it is anchored.

Suggested direction

The renderer is a service and belongs in AppSession alongside the other eight, reaching the control the way every other dependency reaches a view — through the object graph rather than a static. If the cache must stay process-wide for the memory reasons that motivated it, it should at least have an owner that can dispose it.

Status · 2026-09-21

Fixed — todos.md task 45. IDiagramRenderer is a member of AppServices, built in AppSession like every other service. MarkdownView.DiagramRenderer is a StyledProperty bound from MainWindow.axaml, and the caches are instance fields; no static survives.

F9

Sidebar.axaml.cs holds drop policy, filesystem paths and template-private names

MediumConf: HighFixed

Finding. The sidebar code-behind (169 lines, the heaviest in the app) carries behaviour beyond wiring: drop-position rules, path handling, direct view-model mutation, and a dependency on a private part name in the Fluent theme's control template.

Evidence
  • Sidebar.axaml.cs:125-128 — the drop rule is a set of thresholds in the view: a folder row accepts a drop into it between 25% and 75% of its height, otherwise the drop is before or after at the 50% line.
  • :77 and :117 — the drag payload is a filesystem path string, re-resolved through Vm.FindNode(path) on the drop side.
  • :134-138 — RowUnder locates the row by b.Name == "PART_LayoutRoot", an internal name from the TreeViewItem template.
  • Direct view-model mutation at :51 (Vm.SelectedNode), :144/:161 (node.IsDropTarget), :167 (Vm.SearchQuery).
  • :35-36 — PendingDragNode, commented "Test seam", exists for SidebarDragTests.
Why it matters

The genuinely important half of drag-and-drop — where does this land, and is the move legal — is correctly in the view model (MainViewModel.ResolveDrop :414-435, MoveNode :407-408) and is well tested by TreeOrderTests. What remains in the view is the part that decides what the user meant by a pointer position, which is a product rule sitting in an untestable place: the 25/75 threshold cannot be exercised without a pointer-driven UI test, and the app's headless test suite drives it through the test seam instead.

The PART_LayoutRoot dependency is the more fragile item: it is an unversioned internal of the Fluent theme, and a theme update that renames it breaks drag targeting with no compile error.

Suggested direction

Move the "which drop position does this fraction mean" decision to where ResolveDrop already lives, so the view reports a position and the view model interprets it — the seam is already almost there. The template-name lookup is a known Avalonia constraint rather than a design error; it deserves a comment saying so and a test that fails loudly if the name stops resolving, not a redesign.

Status · 2026-09-21

Fixed — todos.md task 43. The drop-threshold rule moved next to ResolveDrop as VaultWorkspaceViewModel.PositionIn(node, fraction) (:332), with IntoBandEdge named rather than written as literals. The sidebar measures the pointer fraction and the view model decides Before / After / Into, so the product rule is unit-testable.

F10

Two error-to-dialog funnels, one of which is documented as the only one

LowConf: HighFixed

Finding. MainViewModel.Guard is documented as "the single place where service exceptions are caught and shown to the user", but a second process-wide handler does the same thing for everything that escapes it.

Evidence
  • MainViewModel.cs:571 — the doc comment: "The single place where service exceptions are caught and shown to the user." Implementation at :572-594.
  • App.axaml.cs:33-37 — Dispatcher.UIThread.UnhandledException sets args.Handled = true and shows the message through the same DialogService.
  • Two further local catch sites deliberately do not use Guard: SearchReplaceViewModel.Rescan (:120-125) routes a bad regex to an inline Error string rather than a dialog — with a comment explaining why — and ReplaceAll/UndoReplace catch and report directly.
Why it matters

The practical risk is small — both funnels show the same dialog — but the claim in the comment is not true, and the second handler swallows everything, including exceptions that indicate a corrupt state in which continuing is worse than crashing. Because it is global and marks every exception handled, it also means a missing Guard on a new code path produces no visible difference during development, which removes the feedback that would otherwise enforce the discipline.

Suggested direction

Keep both — a last-resort handler is correct for a desktop app — but make the roles distinct: the view-model guard handles expected, user-caused failures; the global handler is a crash barrier and should present itself as one. At minimum the comment should stop claiming exclusivity.

Status · 2026-09-21

Fixed — todos.md task 48, keeping both funnels as this finding asked and giving them different jobs and different words. DialogGuard no longer claims to be the only one: its comment now says what a guard is for (a failure a command could see coming, shown in the words it was thrown with) and names the crash barrier as the other path. App.StartDesktop keeps args.Handled = true — a notes app that exits takes the buffer someone was typing into with it — but shows App.CrashMessage instead of the raw ex.Message: it says the failure was not expected, that the app may no longer be sound, and names the exception type. That restores the development feedback the finding said was lost, and ErrorFunnelTests pins it — a guarded failure must not arrive wearing the barrier's words.

F11

A cache-owned bitmap can be disposed while a live view is still drawing it

LowConf: MediumFixed

Finding. DiagramView holds a bitmap reference the LRU owns, and the LRU disposes values on eviction without knowing whether they are in use.

Evidence
  • Lru.cs:20-25 — on overflow, oldest.Value.Value.Dispose() then remove. No in-use tracking.
  • DiagramView.cs:74-81 — Rasterize assigns Bitmap = _cache.GetBitmap(_source, _dark, pixelWidth), storing a cache-owned reference on the view.
  • DiagramView.cs:67-71 — Render draws that stored bitmap on every frame.
  • DiagramCache.cs:19 — the bitmap LRU capacity is 32, keyed by (source, dark, pixelWidth).
Why it matters

If more than 32 distinct (source, dark, pixelWidth) combinations are live at once, one diagram's rasterisation can evict and dispose the bitmap another visible diagram is still drawing. Reaching 32 requires an unusual document — many diagrams, or a window resized through many widths with several diagrams present, since each width is a distinct key. I found no guard, and no test either way.

This is reported at Medium confidence deliberately: the code path is clear, but whether it is reachable in practice depends on realistic document shapes, and the bound was chosen for a measured memory problem rather than arbitrarily.

Suggested direction

Ownership needs to be single-valued: either the cache owns bitmaps and views borrow them for the duration of a single draw, or views own what they draw and the cache is a factory. The current arrangement — cache owns the lifetime, view holds the reference across frames — is the combination that cannot be made safe by tuning the capacity.

Status · 2026-09-21

Fixed — todos.md task 46, after reproducing it with bitmapCapacity: 1. DiagramView keeps only _pixelWidth, the cache key, and borrows the bitmap from the cache for the length of a single Render, which is safe because Avalonia takes its own reference on the draw it records. A key cannot go stale the way a reference can. The same split in ImageCache was found while fixing this one and left; see F4.

F13

Three theming mechanisms, and diagram colours are a second palette

LowConf: HighFixed

Finding. Theme is expressed declaratively through resources, imperatively through a global application property driven per-window, and as a captured boolean baked into diagram rendering — and the third path defines its own colours.

Evidence
  • Declarative: Themes/Palette.axaml:5-15 (light) and :33-43 (dark) define MdSurface, MdText, MdAccent …, consumed by DynamicResource throughout the XAML and imperatively in BlockRenderer/InlineRenderer.
  • Imperative-global: App.ApplyTheme (App.axaml.cs:53-60) writes Application.Current!.RequestedThemeVariant, invoked from AppSession.cs:49 and again from a per-view-model PropertyChanged subscription at :50-54. The target is application-global; the trigger is per-window, so with N windows the last writer wins.
  • Captured snapshot: MarkdownView.cs:80 takes var dark = ActualThemeVariant == ThemeVariant.Dark; into RenderContext, which becomes part of the diagram cache key and reaches MermaiderDiagramRenderer.cs:12-13 — which hard-codes #1E1E1E, #FFFFFF, #DDDDDD, #27272A.
Why it matters

Diagram colours cannot follow the palette, because they are defined in the services layer and the palette is a XAML resource dictionary. Editing Palette.axaml restyles the whole app except diagrams. Separately, theme is per-window state in the view model (MainViewModel.ThemeMode, persisted per user) but application-global in effect, so two windows cannot disagree about it and the loser's persisted setting is silently overridden.

The snapshot-and-rebuild mechanism itself is sound — it is what lets diagrams re-render on a theme change (MarkdownView.cs:39) — and the colour duplication has a real cause: Mermaider needs literal colour strings, which is also why SvgCssInliner exists.

Suggested direction

Let the diagram colours come from the same source as everything else — read from the resolved theme resources at render time rather than restated as literals — so there is one palette. The per-window/global theme mismatch is worth a deliberate decision rather than a fix: either theme is an application setting (and does not belong on MainViewModel), or it is per-window (and RequestedThemeVariant is the wrong mechanism).

Status · 2026-09-21

Fixed in f455fa9 (review phase 1). Models/DiagramPalette.cs carries the colours as the literal strings the renderer needs, and they are resolved from MdSurface and MdText at render time (MarkdownView.cs:119-129) — the hard-coded hexes are now fallbacks only, so editing the palette restyles diagrams too. The per-window theme race went with it: AppSession.cs:41-47 holds one application-wide subscription, and MainViewModel.ThemeMode reads the setting rather than keeping a copy that could disagree.

8Unnecessary Complexity

The honest summary is that this codebase is not over-abstracted. There is no DI container, no repository pattern over the filesystem, no mediator, no event bus, no generic Result<T> wrapper, no plugin system. Services are concrete classes doing concrete work, and the composition root is 85 lines that can be read top to bottom. That restraint is the right call for a 5 000-line app and should be defended.

What genuine excess exists is narrow:

  • Four interfaces buying nothing (F5) — the only clear case of abstraction without a substitution point.
  • DialogService is a forwarding wrapper. All four methods are one-line passthroughs to static factories on the dialog windows (DialogService.cs:26-31 → MessageDialog.ShowErrorAsync, ConfirmAsync, InputDialog.ShowAsync). The class holds no instance state; its only real logic is the static owner-window resolution. The interface earns its keep — FakeDialogs is used by most view-model tests — but the class is a seam with nothing in it.
  • Premature extensibility, documented as such. NoteTemplateService.ContentFor(folderPath, name) ignores folderPath; the doc comment (NoteTemplateService.cs:9-10) says it is "what per-folder templates would resolve against". This is the mildest possible form of the smell — one unused parameter, honestly labelled — and is listed for completeness rather than concern.
  • SettingsViewModel is mostly pass-through. It is a property-by-property re-export of ISettingsService with unit conversion (ms ↔ seconds) and status strings. That is a legitimate job for a view model, but combined with the manual _changed callback and the six explicit OnPropertyChanged calls in Open() (:133-143), it is carrying work that a change-notifying settings service would do for free.

Conversely, several things that look like excess are not, and should not be simplified:

  • The ReadEntries / ReadChildren split in VaultService (:300-333) looks like duplication and is a deliberate correctness boundary — one orders without filtering because that is what .order means, the other filters for the tree. Merging them would silently delete excluded siblings' order lines.
  • The two FileSystemWatchers (:33-56) look redundant and are not: the second is narrowly filtered so that LastWrite notifications do not fire on every autosave.
  • SvgCssInliner looks like something a library should do; PLAN.md records that Svg.Skia has no CSS-variable support and renders Mermaider's output black without it.

9AI-Assisted Development Smells

This section reports observable architectural consequences of rapid iterative development. It makes no claim about how any code was produced.

What the shape of the history shows

PLAN.md's progress log records nine substantial features landing between 2026-09-15 and 2026-09-18: a WPF→Avalonia port, a UI overhaul, two performance fixes, manual ordering, vault-wide search and replace, loose-file handling, configurable autosave, note templates, and vault exclusions. Git history is not usable as corroboration — the repository has two commits, and the two most recent features are entirely uncommitted (13 untracked source files, 32 modified).

The notable thing is what this did not produce. There are no compatibility wrappers, no parallel implementations of the same subsystem, no dead abstraction layers, and no versioned duplicates. PLAN.md even records duplication being found and removed — "ReplaceService.IsHidden … is gone, and its IsUnder was a byte-for-byte copy of PathScope.IsSameOrUnder". Each feature's entry reasons explicitly about where the seam should go, and in several cases argues against the more abstract option.

Where the accumulation is visible

  • Locally-reasonable changes with a collective cost. Each of the last four features added exactly one dependency to MainViewModel, each justified in isolation, and the sum is a nine-argument constructor repeated at ten call sites (F3). No single step was wrong; no step was the moment to split the class either.
  • Each feature brought its own vault traversal. Search walks; replace walks; the quick switcher walks; the exclusion probe walks. Four features, four independent answers to the same question, none of them wrong on its own (F2).
  • Three overlays, three copies of the same chrome (F12) — the quick switcher came first, and search-and-replace and settings each started from it. The divergence has already begun: only the settings panel has the focus-commit fix.
  • Documentation mass exceeds source mass. STRUCTURE.md (162 KB, 3 483 lines), todos.md (77 KB, including two full reviewer logs inline) and PLAN.md (39 KB) total roughly 280 KB against ~180 KB of C#. STRUCTURE.md is a generated index that drifts against the code between regenerations.
  • Test organisation drifting from test content. SettingsViewModelTests lives inside AutoSaveTests.cs:222 — it was added when the autosave settings were, and stayed there through two subsequent features that extended it. PLAN.md refers to it as though it were its own file.
  • Test seams in production API surface. Sidebar.PendingDragNode and DiagramView.Bitmap are public members that exist for tests (F9) — a reasonable trade for testing pointer-driven code, worth naming because it is the kind of thing that multiplies.
The distinguishing observation. The usual signature of accumulated AI-assisted development is layers — new abstractions stacked on old ones, wrappers whose purpose has expired. That pattern is absent here. What this codebase shows instead is breadth: nine features that each reached correctly into the same two structural points — MainViewModel's constructor and the vault's traversal — because neither was ever refactored to accommodate the fourth caller. The architecture did not decay; it simply stopped being resized.

10Positive Architectural Decisions

Strict, verified layer direction

Not one Avalonia type in Services/ or Models/. This is the single most valuable property of the codebase: the ignore-pattern language, the template substitution rules, the match finder, the diacritic folder and the whole vault API are testable without a UI toolkit, and 31 test files exploit that. Preserve it unconditionally — including in any fix to F4.

One class per filesystem convention

IgnoreFile owns the names .mdnotesignore/.gitignore and never throws; FolderOrderFile owns the .order format and the folder-suffix convention; PathScope owns containment; DiacriticFolder owns folding. Each carries an explicit "the only code that knows this" contract in its doc comment, and each is actually honoured. This is what makes the exclusion feature a three-call-site change rather than a rewrite.

MatchFinder as a single matcher behind preview and write

The replace preview and the replace itself go through the same code, so the user cannot be shown one thing and have another written. ReplaceService.StillMatches (:70-78) then re-verifies every span against the file's current bytes before writing and reports skipped notes by name. This is a real correctness invariant, deliberately constructed, and the undo snapshot travels in the report so the service stays stateless.

The SaveImplicitly gate

Every write the user did not explicitly ask for passes through one method that is a no-op in manual mode (EditorViewModel.cs:102-105), with the prompting path separated into FlushUnsavedAsync. Eight call sites, one rule, no leakage. Autosave semantics are the kind of thing that usually ends up scattered; here it did not.

Ordering before filtering, with a test named after the trap

VaultService.ReadEntries deliberately does not apply exclusions because .order must record every sibling; ReadChildren filters for the tree; and VisibleToFull (:339-350) translates a sidebar row index into a disk index. Without this, one drag in a folder with an excluded sibling would delete that sibling's order line permanently. The reasoning is recorded, the regression test exists, and the trap is named.

Explicit composition root, no container

AppSession.cs is 85 lines in which every dependency is visible. For an app this size a DI container would obscure more than it automates. Do not add one.

Callback-based child view models

QuickSwitcherViewModel and SearchReplaceViewModel receive Action delegates rather than a reference to their parent (MainViewModel.cs:85-99). No cycles, and each is constructible in a test with two lambdas — which is why QuickSwitcherViewModelTests and SearchReplaceViewModelTests exist as focused unit tests while the shell needs a headless window.

Decisions are recorded with their reasoning

PLAN.md explains not only what was built but what was rejected and why — why ! negations are unsupported, why the vault must not read settings, why substitution is one regex pass rather than chained Replace, why an unrecognised placeholder is returned verbatim. This is genuinely rare and it is what made this review possible at this level of confidence. It is also the thing most likely to be lost: it lives in one 39 KB file rather than beside the code it governs.

13Overall Architecture Assessment

Is the architecture coherent?

Yes. The layering is real, not aspirational — it is enforced by what the files actually reference, and it holds at every boundary but one (F4, a single method in the inline renderer). The filesystem-as-truth model is applied consistently; there is no shadow state to reconcile. Someone reading this codebase for the first time can follow any feature from keystroke to disk without encountering an indirection that does not pay for itself.

Where is complexity concentrated?

In two places, both of which are convergence points rather than tangles:

  • MainViewModel — 595 lines, 12% of the source, every feature's entry point. It is not badly written; it is simply where everything meets, and nothing has been moved out of it since the Avalonia port.
  • Vault traversal — VaultService is correct and carefully built, but four features each added an independent walk over it rather than a shared question. There is no index and, more to the point, nowhere an index could currently live.

The view layer's complexity is of a different kind: not concentrated but replicated — three overlays, three theming mechanisms, five copies of the DataContext cast. It is cheaper to fix and cheaper to ignore than the other two.

What is designed versus accumulated?

Designed, clearly: the layer boundaries; the one-class-per-convention rule for filesystem formats; MatchFinder as a shared matcher; the SaveImplicitly gate; the order-before-filter split; the callback-based child view models; the decision not to use a DI container. Each of these has explicit reasoning recorded in PLAN.md, and each holds under inspection.

Accumulated: MainViewModel's dependency list; the four independent traversals; the overlay triplication; the per-window/global theme mismatch; the four unused interfaces — which likely date from the WPF-era service layer, where the renderer genuinely did return HTML and a second implementation was plausible.

The distinction is unusually clean here, which is a compliment to the documentation: the designed parts were argued for in writing, and the accumulated parts are precisely the ones no entry in PLAN.md ever revisited.

What deserves human investigation first?

  1. F1 — shared vault identity. It is the only finding that can produce wrong behaviour, it affects saving, and it will get worse as more per-window state is derived from the shared root. Start with the decision — shared or per-window — not with the code.
  2. F2 — no place to put an index. Not urgent as a performance matter, but it is the constraint that will shape the next feature: backlinks, tags, and note counts all need to ask the vault a question, and today the only available answer is a fifth full walk.
  3. F3 — MainViewModel's growth vector. Cheap to defuse (a test helper), expensive to fix properly (a split). The cheap step buys time honestly; it should not be mistaken for the fix.
Closing. The instinct to preserve here is stronger than the instinct to change. The layer discipline, the single-owner filesystem conventions, the shared matcher and the save gate are better than one typically finds at this scale, and every one of them would be easy to lose in a well-intentioned refactor. The three items above are worth deliberate attention. Almost nothing else in this report is worth acting on before them.
